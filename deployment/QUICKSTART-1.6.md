# SubnetDesk Management Console 1.10.1 Build125 — Agent 1.7.0 — Helper 1.4.5

## جديد Build125

- شعار Deploy يحمل شارة نشر ذهبية لتمييزه عن Helper في التطبيق والاختصار والمثبّت.
- **Manage credentials** يتيح اختيار ملف اعتماد محفوظ وتعديله وحذفه بأيقونة سلة المهملات مع تأكيد الحذف.
- الأسماء المكررة مرفوضة، مع تجاهل اختلاف حالة الأحرف والمسافات في بداية الاسم ونهايته.
- زر العين يُظهر أو يُخفي كلمة المرور المُدخلة. كلمة المرور المحفوظة لا تُعاد للواجهة؛ عند تعديل الملف اترك الحقل فارغاً للاحتفاظ بها إذا لم يتغير الحساب.
- لا يُحذف ملف اعتماد مرتبط بمهمة معلقة/قيد التنفيذ أو بجدول، ولا يُعدّل أثناء وجود مهمة معلقة/قيد التنفيذ تستخدمه.
- نتائج الاكتشاف الجديدة تعرض رمز خطأ Windows مع عدد العناوين المتأثرة وأمثلة عليها. النتائج القديمة تبقى كما سُجلت؛ أعد الفحص للحصول على التشخيص المفصّل.

## اكتشاف Windows ودفع Agent وجدولة العمليتين

من **Agent deployment**:

1. احفظ حساب إدارة **Local administrator** باسم المستخدم فقط، مثل `Administrator`،
   أو **Domain administrator** بصيغة `DOMAIN\user` أو `user@domain` وكلمة مرور Windows.
   يحفظ الخادم الملف مشفراً بـWindows DPAPI لتعمل الجداول دون إبقاء الواجهة مفتوحة.
2. أدخل نطاقات VLAN الموجّهة، مثل `192.168.50.0/24`، أو نطاقاً كاملاً مثل
   `192.168.60.10-192.168.60.200`، أو أسماء أجهزة، كل نطاق في سطر.
   **Suggest connected subnets** يقترح شبكات واجهات الخادم فقط؛ لا يكتشف جميع VLANs المؤسسة تلقائياً.
3. **Discover Windows / test credentials** يفحص الإدارة الموثّقة عبر WMI/RPC.
   تظهر أجهزة Windows المؤكدة فقط. فشل الفحص لا يثبت أن الجهاز مطفأ أو أنه ليس Windows.
4. حدد الأجهزة، حتى 600 جهاز أو أكثر، ثم **Push Agent**. عدد العمليات المتزامنة
   منفصل عن العدد الإجمالي، وبقية الأجهزة تنتظر في الطابور.
   يعاد فحص اسم الجهاز وUUID قبل نسخ المثبّت إلى `ADMIN$` وتشغيله صامتاً.
   عنوان خادم الإدارة وبصمة شهادته يُمرران تلقائياً؛ لا تمرر كلمة مرور الإدارة إلى سطر أوامر الهدف.
5. **Schedule discovery** يحدد موعداً وتكراراً للفحص. **Schedule push** يحفظ
   موعداً وتكراراً مستقلين للأجهزة المحددة وقت إنشاء الجدول؛ الأجهزة المكتشفة لاحقاً لا تُضاف تلقائياً.
   يمكن إيقاف/استئناف كل جدول. تعطيل الجدول يمنع التشغيلات القادمة؛ ألغِ المهمة الموجودة منفصلاً.
   المواعيد المتأخرة تُدمج في تشغيل واحد، ولا تُكرر مهمة الجدول وهي منتظرة أو قيد التنفيذ.
6. راجع **Agent requests** ووافق على التسجيلات الجديدة. نجاح التثبيت وتشغيل الخدمة
   لا يعني أن التسجيل قد تمت الموافقة عليه. بعدها تستطيع إدارة تثبيت/تحديث/حذف Helper من Devices.

تُنفذ الجداول في خدمة الإدارة عند إغلاق الواجهة، ويجب أن يبقى الخادم قيد التشغيل.
تعرض نافذة إنشاء الجدول الوقت المحلي؛ يحفظ الخادم UTC، وتعرض قائمة الجداول الموعد بصيغة UTC.
المهام التي انقطعت أثناء إعادة تشغيل الخدمة لا تُعاد تلقائياً لأن نتيجة التثبيت قد تكون غير معلومة.

يتطلب الدفع اتصالاً موجّهاً، وRPC/WMI (TCP135 ومنافذ RPC الديناميكية) وSMB445 و`ADMIN$`
وصلاحيات الإدارة على الهدف. قد يمنع Remote UAC الحساب المحلي حتى لو كانت كلمة المرور صحيحة.
لا تُعطّل الأداة UAC أو الجدار الناري تلقائياً. راجع
[متطلبات WMI الرسمية](https://learn.microsoft.com/en-us/windows/win32/wmisdk/securing-a-remote-wmi-connection)
و[قيود UAC](https://learn.microsoft.com/en-us/windows/win32/wmisdk/user-account-control-and-wmi).
لا يتطلب هذا المسار WinRM أو منفذ5986. بعد التثبيت يحتاج Agent الوصول إلى HTTPS443 على خادم الإدارة؛
قد تحتاج قواعد شبكة تسمح بنطاقات VLAN الموجّهة، لأن إعداد الخادم الافتراضي يسمح بالشبكات المحلية فقط.

التحقق الآلي لهذا الإصدار يستخدم نقل WMI/SMB وهمياً، ولم تُنفذ تجربة دفع فعلية إلى أجهزة المؤسسة.

## ترقية جهاز الإدارة

1. أغلق Deploy القديم وثبّت `SubnetDesk-Deploy.msi` الجديد.
2. افتح **SubnetDesk Deploy** من Start. سيطلب Windows صلاحية المسؤول.
3. ستفتح لوحة Overview، وتُحمّل الأجهزة الحالية والمهمات المحفوظة تلقائياً.
4. من **Server & enrollment → Configure / repair server** اختر اسم الخادم الحالي
   وعنوان واجهة الشبكة المحلية. مثلاً `PC-Aysar` و`192.168.50.189`.
   لا تغيّر اسم خادم مُسجّل عشوائياً: الشهادة وهويات الأجهزة مرتبطة بإعداده.

إصلاح الإعداد يحافظ على التسجيلات، ويهيّئ IPv4 وIPv6 وقاعدة 443 لواجهة LAN
المختارة. الأجهزة على شبكات موجّهة أخرى تحتاج نطاق مصدر مسموحاً مناسباً في
الجدار الناري. يبقى خادم الإدارة يعمل عند إغلاق الواجهة.

## قائمة الأجهزة الموحدة

قسم **Devices** يعرض أجهزة Agent وأجهزة Domain / WinRM مع نوع الإدارة والحالة
والنسخ والمجموعة وآخر اتصال أو فحص. يمكن البحث والفلترة والتحديد الجماعي،
وتغيير الاسم والمجموعة، وعرض التفاصيل وتصدير CSV.

زر **Columns** يتيح إظهار وإخفاء 21 حقلًا، منها نسخة Agent وWindows، واسم
الكمبيوتر وعنوانه، ونسخة وخدمة Helper، والدومين، والمعمارية، وحالة المهمة.
اضغط عنوان أي عمود بيانات للفرز تصاعدياً أو تنازلياً. الفرز يشمل كل النتائج
قبل تقسيم الصفحات؛ النسخ والعناوين تُقارن رقمياً، وLast seen يُفرز بالتاريخ
الفعلي. تُحفظ اختيارات الأعمدة والفرز لكل مستخدم على جهاز Deploy.
يمكن **Show all** أو **Reset defaults**، ويجب إبقاء عمود بيانات واحد على الأقل.
تصدير CSV يتبع الأعمدة الظاهرة وترتيب الفرز الحالي ويشمل كل النتائج المطابقة.

**Online** للـAgent يعتمد على آخر Heartbeat. **Ready** للدومين يعني أن اختبار
WinRM الموثّق نجح حديثاً؛ الدومين لا يرسل Heartbeat بدون Agent.
نتيجة فاشلة لا تعني تلقائياً أن الجهاز مطفأ: قد تكون الصلاحيات أو الشهادة سبباً.

## إضافة Agent — نفس المثبّت لجميع الأجهزة وموافقة من السيرفر

1. **Add devices → Install Agent on devices**.
2. صدّر **reusable Agent setup**. تحصل على ملف EXE واحد يحتوي عنوان الخادم وبصمة شهادته فقط.
3. استخدم نفس الملف على جميع الأجهزة، بما فيها 600 جهاز. لا يوجد كود تسجيل ولا مهلة 24 ساعة.
4. افتح المثبّت على الجهاز الهدف، ثم **Install & connect**.
5. في Deploy افتح **Agent requests**، راجع اسم الجهاز وعنوانه وحدّده ثم **Approve selected**.
   يمكن الموافقة أو الرفض جماعياً. الطلب المعلّق لا يملك صلاحية تنفيذ الأوامر أو تنزيل الحزم.

لا يحتاج الجهاز JSON أو أوامر PowerShell. يثبت Agent خدمة Windows، ويسجّل
نفسه في Apps & Features، ويضيف **SubnetDesk Agent Settings** إلى Start.
تستمر الخدمة بعد إغلاق نافذة الإعدادات، وتُشغّل مع Windows.

كل جهاز ينشئ هويته ومفتاحه الخاص محلياً. السيرفر يحتفظ ببصمة المفتاح فقط.
طلبات الموافقة صالحة سبعة أيام. يمكن مقارنة بصمة Verification في Diagnostics
مع الطلب في Deploy للتأكد من الجهاز. الموافقة لا تستلزم إدخال أي كود.
عند استخدام EXE غير مُجهّز، اكتب اسم السيرفر وأكّد بصمة شهادته بعد مقارنتها
بقسم Server & enrollment؛ المثبّت المُجهّز يوفر هذه الخطوة.

لتحديث Agent قديم على نفس الخادم: افتح EXE الجديد واضغط **Save & reconnect**
دون تغيير التسجيل. إذا كانت هويته ملغاة **Revoked**، اضغط **Request server approval**
على الجهاز ثم وافق على طلبه الجديد في Deploy؛ لا يُعاد تفعيل الهوية الملغاة تلقائياً.

## إضافة أجهزة الدومين بدون Agent

1. **Add devices → Add domain / WinRM computers**.
2. اكتشف الأجهزة من Active Directory بحسابك الحالي، أو استورد أسماء الأجهزة.
3. حدّد الأجهزة ثم **Device actions → Verify domain connections**.
4. أدخل حساب الدومين الإداري لهذه العملية. لا تُحفظ كلمة المرور.

الاستيراد لا يفعّل WinRM تلقائياً ولا يثبت أهلية الإدارة. يلزم تهيئة HTTPS
والشهادة والصلاحيات والجدار الناري. يمكن تحضير HTTPS عبر Kerberos إذا كانت
قناة إدارة أولية متاحة، باستخدام اسم DNS.

## إدارة Helper

قسم **Helper packages** يحفظ مكتبة إصدارات MSI على الخادم. اختر الإصدار، ثم
الأجهزة من Devices وإجراء من **Device actions**:

* Install / update، Repair، Uninstall.
* Start، Stop، Restart لخدمة Helper.

تُطلب موافقة صريحة قبل الحذف أو إيقاف الخدمة. حذف Helper لا يحذف Agent.
أجهزة Agent غير المتصلة تحتفظ بالمهمة حتى تتصل. مهام الدومين تعمل من الواجهة
مباشرةً، لذلك أبقِها مفتوحة حتى تنتهي العملية.

**Tasks & history** يعرض الأعمال النشطة وآخر 200 نتيجة. يمكن إلغاء مهمة
Agent المنتظرة فقط، ولا يُقطع MSI بعد بدء تنفيذه. يبقى سجل النتائج الكامل
محفوظاً على الخادم. إلغاء صلاحية Agent يختلف عن حذفه من قائمة الجرد أو إزالة
برنامجه من الجهاز.

## كلمة مرور Unattended Access

أثناء **Install / update Helper** فعّل **Set unattended access password** وأدخل
كلمة المرور وتأكيدها. يمرّر Deploy الخصائص المدعومة إلى Helper MSI؛ حزمة
Helper 1.4.4.104 تدعمها. أجهزة Agent تحتاج Agent 1.5.0+، وإلا تُتخطّى المهمة
مع بيان السبب بدلاً من تثبيت Helper دون كلمة المرور المطلوبة. مسار WinRM
يدعم إعداد كلمة المرور أثناء التثبيت أيضاً.

بعد التثبيت: حدّد أجهزة Agent ثم **Device actions → Helper security settings → Change unattended access password**.
يجب أن يكون Helper مثبتاً وخدمته تعمل. تُحفظ الكلمة عبر أمر Helper المخصص
بإدخال stdin، ثم يُعاد تشغيل خدمة Helper لتحميلها؛ قد تنقطع جلسات Helper
القائمة، بينما يبقى Agent مستقلاً ومتصلًا. تُطبّق الكلمة حتى إن كانت نسخة MSI
نفسها مثبتة بالفعل.

المهام الحساسة محمية بـWindows DPAPI في طابور السيرفر، وتُحذف حمولة كلمة
المرور عند النتيجة أو الإلغاء أو إلغاء الصلاحية أو انتهاء المهلة. لا تظهر
في الجرد أو سجل المهام. تنتهي المهمة الحساسة بعد 24 ساعة. Base64 المستخدم
لخاصية MSI ترميز فقط وليس تشفيراً؛ الحماية أثناء النقل هي HTTPS.

هذه كلمة مرور الوصول غير المراقب، وليست كلمة مرور مسؤول Windows ولا كلمة
مرور فك قفل Receiver-only. إدارة قفل الجهاز موضّحة في القسم التالي، وتستخدم كلمة مرور مستقلة عن الوصول غير المراقب.

اختُبرت الواجهة وخصائص MSI وعقود الطابور والتسليم والحذف وحماية الأسرار، دون
تغيير كلمة مرور جهاز إنتاج فعلي أو اختبار تسجيل دخول فعلي بالكلمة الجديدة.

## سياسة Receiver-only لكل الجهاز وكل حسابات Windows

من Helper 1.4.5 Build121، كل تثبيت أو إعادة تثبيت أو إصلاح أو ترقية يعيد قفل Receiver-only لجميع الحسابات، حتى لو كان الجهاز مفتوحاً سابقاً من Deploy. تبقى الهوية وكلمة Unattended ومعرّف كلمة فك القفل المخزّن محفوظة. فك القفل بعد التثبيت يبقى عبر إعادة التشغيل العادية، ويعاد القفل عند تشغيل المثبّت التالي.


1. حدّث Deploy إلى 1.9.0 وAgent إلى 1.6.0. يمكن تحديث Agent 1.4.0+ من **Agent updates**.
2. اختر **SubnetDesk-Helper.msi 1.4.5** من مكتبة Helper وثبّته/حدّثه على الأجهزة.
3. من Devices حدّد أجهزة Agent ثم **Device actions → Helper security settings**.
4. اختر الإجراء: **Lock all accounts as receiver-only** أو **Unlock all accounts to
   send-and-receive** أو **Change device receiver unlock password**.

القفل المركزي الأول يعتمد كلمة المرور الجديدة التي تختارها ويستبدل اختلاف
إعدادات الحسابات المحلية بسياسة واحدة. بعد وجود سياسة مقفلة، تغيير كلمة مرورها
يتطلب الكلمة الحالية؛ لا يمكن تجاوز ذلك بإعادة إرسال أمر القفل بكلمة مختلفة.
فك القفل يتطلب الكلمة الحالية أيضاً، وتغييرها لا يغيّر وضع القفل/فتح القفل.
عند أول فك قفل/تغيير للكلمة قبل وجود سياسة مركزية، تُتحقق كلمة قفل خدمة Helper الحالية.

السياسة تشمل الحسابات الحالية والجديدة وتُحفظ بعد إعادة التشغيل وترقية Helper.
تقرأها البرامج من إعداد جهاز محمي؛ حسابات المستخدمين العادية تملك صلاحية القراءة
فقط. يعرض Helper أن السياسة مُدارة من Deploy ويمنع الإعداد المحلي من تجاوزها.
تُطبّق على الاتصالات الصادرة الجديدة؛ الجلسات القائمة لا تُقطع قسرياً، وقد تحتاج
إعادة فتح نافذة Helper لتحديث تخطيطها. كلمة مرور Unattended لا تتغير بهذه الإجراءات.

القائمة والتفاصيل تعرضان **Device receiver mode** و**Receiver policy scope**، ويمكن
إظهارهما/إخفاؤهما من Columns. الأجهزة غير الداعمة تُتخطّى بسبب واضح، ولا يُكتفى
بتغيير إعداد حساب خدمة النظام. الترقية تحفظ ملف إعدادات Helper؛ التثبيت بعد إزالة
كاملة ينشئ ملفاً جديداً، مع بقاء السياسة المركزية المقصودة على مستوى الجهاز.
إزالة Agent لا تلغي سياسة الجهاز؛ تُستعاد إدارتها بتثبيته مجدداً أو بإجراء مسؤول
النظام الموثق في README.

اختبارات Rust وC# تغطي الأولوية على إعدادات الحسابات، كلمة المرور الخاطئة،
الدوران مع الحفاظ على الوضع، الحفظ واستعادة الحالة، وصلاحيات القراءة فقط.
اختبارات الواجهة وHTTP تغطي الإجراءات وفحص التوافق وحماية الأسرار. اختبار
التثبيت والتبديل الفعلي بين حسابين مختلفين على جهاز هدف يبقى مطلوباً.
## حدود الإصدار والفحص

في Agent 1.3.1 يظهر اسم Windows الفعلي وإصداره ورقم البناء بدل Windows NT.
عند تغيير IP الجهاز الهدف، يُحدّث السيرفر عنوان مصدر اتصاله التالي دون إعادة
تسجيله. وبعد تغيير اسم Windows وتطبيقه (قد يتطلب إعادة تشغيل Windows)، يُحدّث
اسم الكمبيوتر في السجل نفسه. يبقى الاسم المخصص الذي وضعه المسؤول محفوظاً،
ويظهر الاسم الفعلي في Computer name. الهوية والمهام مرتبطة بمفتاح الجهاز لا بـIP أو الاسم.

إذا تغير IP سيرفر Deploy، يجب أن يحل اسم الخادم المحفوظ لدى Agent إلى عنوانه
الجديد وأن يبقى HTTPS متاحاً. عند استخدام عنوان IP حرفي بدلاً من اسم DNS،
تحتاج مراجعة عنوان السيرفر وشهادته وإعداد Agent؛ لا نفترض أنه سيتغير تلقائياً.

اختبار HTTP محلي معزول مرّر اتصالات فعلية IPv4 ثم IPv6 ثم IPv4 مع أسماء مختلفة،
وتحقق من تحديث العنوان والاسم وبقاء الهوية والمجموعة والمهمة وعدم تكرار السجل.
هذا ليس تغيير DHCP أو اسم جهاز إنتاج فعلياً، ولا اختبار نقل خادم الإدارة إلى عنوان جديد.

لا يدّعي هذا الإصدار مطابقة Kaspersky/Intune وظيفياً. إدارة المشغّلين المتعددين
بصلاحيات RBAC وMFA، والتوقيع الإلزامي للحزم، وجدولة تحديث Agent تلقائياً، وتجديد
الشهادات تلقائياً، وجدولة الصيانة، والتحكم العام بكل برامج Windows ليست ميزات
مسلّمة حالياً. نطاق الأوامر البعيدة محصور بإدارة Helper وتحديث Agent.

اختبارات الواجهة تشمل الفلترة والتحديد الجماعي لـ600 جهاز وحالات الخطأ،
واختبارات التخزين تشمل الجرد والطوابير والإلغاء والتسجيل. صور الفحص المرئي
تستخدم بيانات اختبار، ولا تمثل جرد شبكة حقيقية. فحص التثبيت وإعادة التشغيل
والنشر والحذف على جهاز Windows هدف فعلي ما زال مطلوباً.

## تحديث Agent من لوحة الإدارة

نسخ Agent حتى 1.3.x لا تنفذ أمر تحديث نفسها. افتح Agent 1.4.0 مرة واحدة على
الجهاز واضغط **Save & reconnect** مع إبقاء التسجيل نفسه. من هذه النسخة يصبح
تحديث الإصدارات الأحدث متاحاً من الداشبورد دون زيارة الجهاز.

1. حدّث Deploy إلى 1.7.0 ثم افتح **Agent updates**.
2. ارفع EXE إصدار Agent أحدث، أو اختر **Use bundled Agent**، ثم **Select**.
3. حدّد الأجهزة من **Devices** ثم **Device actions → Update Agent**، أو ارجع
   إلى Agent updates واضغط **Queue Agent update**.
4. راقب **Tasks & history**: التنزيل، التحقق، إعادة تشغيل الخدمة، ثم النتيجة.

الأجهزة غير المتصلة تنتظر الاتصال التالي. يُتخطّى الإصدار نفسه أو الأقدم،
والأجهزة الملغاة أو المشغولة أو غير الداعمة. مكتبة Agent مستقلة عن Helper.
يُحمَّل الملف عبر HTTPS مع التحقق من البصمة ونوع الحزمة والنسخة. تُحفظ نسخة
من البرنامج السابق لاسترجاعها إذا فشل بدء الخدمة الجديدة. لا تُغيّر العملية
ملف الهوية أو إعداد السيرفر أو Helper. لا تحتاج كود تسجيل أو موافقة جديدة.

الاختبارات الحالية تشمل نقل الحزمة والطابور والصلاحيات والتحقق من النسخة
ونتيجة المهمة عبر HTTP محلي، واستبدال الملفات واسترجاعها. دورة تحديث خدمة
Agent الفعلية عبر SCM على جهاز هدف لم تُختبر بعد. التحقق بالبصمة لا يعادل
توقيع ناشر Authenticode؛ فرض توقيع الناشر ما زال خارج هذا الإصدار.
